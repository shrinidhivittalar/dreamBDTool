# Business Rule Assumptions

The following rules are not fully specified and are intentionally explicit for review:

- **Budget range:** The client gives `budget_min`/`budget_max` instead of a single number plus a buffer percentage. Totals inside the range score highest (best at the midpoint); totals outside either edge are scored with a steeper penalty the further out they go. Nothing is ever excluded for falling outside the range — the goal is to still surface a near-miss option rather than hide it.
- **GST:** DaD Selling Price is assumed GST-exclusive by default (5% added on top before comparing to the budget range) — this rate and default direction are guesses pending finance/CEO confirmation. Since it was ambiguous, `price_includes_gst` is a per-request toggle (BD can flip it) rather than a hardcoded assumption baked into every quote.
- **Sweet preference:** A dedicated `sweet_preference` field (`any` / `sweet_only` / `no_sweet`), separate from the general `preferred_categories` filter, per the original PRD's "preferred sweet / no sweet" requirement. Matches the same category/tag substring logic as everything else ("sweet").
- **Mandatory vs. preferred products:** Split into two fields. `mandatory_products` must match exactly one catalog item (exact name match, or an unambiguous substring match) and is fixed into every recommendation — an unmatched or ambiguous name is a request error (HTTP 400). `preferred_products` is a soft scoring nudge (lenient substring match) and never filters out a combination.
- **Search:** Exhaustive — a dynamic-programming search considers every reachable combination of the filtered catalog (no candidate cap), rather than brute-forcing `itertools.combinations` over a truncated pool. Prices are bucketed to whole rupees for the search; if the catalog/item-count grows large enough that the search grid would be too large, the bucket width doubles automatically (documented in `recommender.py` as `CELL_BUDGET`) — displayed prices always use the exact, unrounded value regardless of bucket width.
- **Scoring weights:** In-house sourcing +3, `Healthy` tag +2, matched preferred product +5, layered on top of the 0-100 buffer-closeness score. These weights are a starting guess, not confirmed with BD.
- **Top-5 diversity:** Results are chosen to avoid heavy product overlap with each other (no more than 25% of the non-mandatory slots shared between two recommendations) so the 5 options are meaningfully different, not near-duplicates. This only applies among candidates scoring within 85% of the best score — a search for variety can't drag in a dramatically worse-fitting combo just because it doesn't overlap with the good ones; once nothing left clears that quality floor, remaining slots are filled by score alone.
- **Product repeats:** Off by default — a product may appear only once in a box. When the BD user enables `allow_repeats`, the same product can be selected more than once to help reach budget on a catalog with a low price ceiling; `item_count` is never changed by this, repeats just fill the existing slots.
- **Required categories (quota slots):** `required_categories` is a hard, count-based constraint distinct from `mandatory_products` — e.g. requesting `["Brownie", "Cookie"]` guarantees at least one Brownie-matching and one Cookie-matching product in every recommendation, but *which specific product* fills each slot is chosen by the optimizer, not the caller. Repeating a category string requests multiple slots of that category. A single product use fills at most one quota slot per unit, even if it matches several requested categories — with repeats enabled, though, the same product can be used again as a separate unit to fill a second slot. A category with zero matching catalog items is a request error (HTTP 400); at most 6 distinct requested categories are supported per request, mirroring the existing `item_count <= 20` bound (a request-shape limit, not a candidate-dropping cap).
- **Achievable-max hint:** If the highest total price reachable for the given item count/constraints falls more than 5% short of `budget_min`, the response's `message` explains the catalog's price ceiling (e.g. "the priciest valid N-item combination is ₹X") instead of silently showing a large unused-budget gap. The 5% threshold is a guess, not confirmed with BD.
- **Category/vendor matching:** User values use case-insensitive substring matching.
- **Occasion:** The field is accepted by the API but is not used because the catalog has no occasion column or rule mapping. Removed from the UI so it doesn't imply a feature that doesn't exist. Deliberately still deferred, not built.
- **Health ranking:** A product is considered healthier when its tags contain `Healthy`.
- **In-house ranking:** A product is considered in-house when its sourcing contains `In-house` or its vendor contains `Dream a Dozen`.
- **Rock Bottom Price validation:** If a row's Rock Bottom Price is greater than its Selling Price (a data error), the value is treated as unknown (`None`) rather than dropping the whole product — the field isn't used by the recommender yet (reserved for a future negotiation feature), so a bad value there shouldn't remove an otherwise-valid, actively-used product.
- **Duplicate catalog rows:** Products are deduplicated by name (case-insensitive); the first occurrence in the sheet wins and later duplicates are dropped at load time.
