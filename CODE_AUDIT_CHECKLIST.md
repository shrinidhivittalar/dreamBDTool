## Broken

- [ ] `backend/recommender.py:301-305` — `_recommend_any_count` passes the fixed constant `MAX_ITEM_COUNT` (10) as `k` to `_select_diverse` regardless of each candidate's actual item count; `_pick_within_threshold` divides overlap by that same `k`, so a 1- or 2-item combo's overlap is understated by 5-10x (two identical 2-item boxes score `2/10=0.2`, under the strictest `0.25` threshold) and near-duplicate small boxes pass the diversity filter as if distinct.
- [ ] `backend/recommender_constraints.py:111-118` — the mandatory-item category-exclusivity check still hard-forbids every pool product sharing *any* broad category with a mandatory item (the old, unconditional cap=1 rule); this was never updated when `category_repeat_cap` was generalized in `_search_unique_pool`, so a mandatory Savoury item silently forbids all other savoury pool items even for box sizes where a cap>1 should legitimately allow more.
- [ ] `frontend/src/lib/briefForm.js:74-77` — a "Must Include" entry in **Preferred** mode is routed straight to `preferred_products` without ever calling `classifyMustInclude`; a category typed and marked Preferred (e.g. "Sweet") is sent as a literal product-name search the backend won't find, instead of being treated as a soft category preference — silent, guaranteed mismatch for a real, expected user action.
- [ ] `backend/catalog_loader.py:110` — `price = float(row[price_column])` isn't guarded by `pd.isna()`; a blank selling-price cell is NaN, `float(nan)` doesn't raise, and `if price < 0` is also `False` for NaN, so a row with a missing price silently becomes a `Product` with `selling_price = nan` instead of being skipped into `skipped_rows`.
- [ ] `backend/catalog_loader.py:126-130` — same NaN gap for `rock_bottom_price` (contrast with `packaging_addon_cost` at line 134, which correctly checks `pd.isna(...)` first).
- [ ] `backend/app.py:70-75,90` — `_humanize_warning` only special-cases `preferred_category_missing` and `budget_exceeded`; the validator's third warning code, `invalid_category` (`validator.py:73-80`), falls through both branches with an empty `key` and renders as a blank segment — a real validation warning is silently erased from the user-facing message.
- [ ] `backend/app.py:258-283` (`export_recommendation_file`) — an empty `recommend()` result has no blocking errors, so the endpoint silently exports a file with zero recommendations instead of surfacing "No valid combinations found" the way the other two call sites do.

## Wrongly wired

- [ ] `backend/recommender.py:123-128` (comment) vs `:129-146` (code) — the comment documents "at most two tries of the capped search before falling back," but the code only calls `search(...)` once before falling straight through to the fully-unconstrained path; there's no intermediate looser-cap retry, so a `cap=1` miss on a small box jumps to zero category-repeat constraint far more often than the documented design intends.
- [ ] `backend/data_provider.py:246` — `self._using_cache = bool(current_products)` reports `using_cache: true` whenever any products remain after a failed refresh, even when the products in memory actually came from the CSV fallback or a prior successful Zoho pull, not the on-disk cache — misrepresents data provenance in the one signal the frontend has for it.
- [ ] `backend/app.py:90` — `_humanize_warning`'s fallback returns `key`, which is `""` for every code except `preferred_category_missing`; any future validator warning code added without a matching branch here silently disappears (this is the direct mechanism behind the `invalid_category` bug above, and will recur for the next new code too).

## Could be better

- [ ] `backend/recommender.py:168-172` — the "even stride across the full result space" sibling-substitution sampling degenerates to just the first `MAX_SIBLING_BASE_COMBOS` combos (not a spread sample) whenever `len(combos)` is between `MAX_SIBLING_BASE_COMBOS + 1` and `2 * MAX_SIBLING_BASE_COMBOS - 1`, contradicting the comment's claim.
- [ ] `backend/recommender_search.py:63-75` — the adaptive `bucket_width` doubling loop has no assertion that hitting the `>= 1000` width cap actually keeps cell count under `CELL_BUDGET`; it silently accepts whatever cell count results, a fragile "give up bounding" escape valve rather than a guaranteed budget.
- [ ] `backend/business_rules.py:12-14` — `IN_HOUSE_WEIGHT`/`HEALTHY_WEIGHT`/`PREFERRED_WEIGHT` duplicate the same constants in `recommender_config.py:3-5`; a change to one set silently diverges from the other.
- [ ] `backend/business_rules.py:17,20-21` — `UNIQUE_CATEGORY_GROUPS` and `THEMED_CUSTOMISED_*_MARKERS` duplicate `recommender_config.py:64,68-69` verbatim; same drift risk.
- [ ] `backend/validator.py:43` — brittle float-equality check (`remaining_budget` vs a freshly-rounded recompute) with no tolerance; a rounding-mode mismatch would raise a blocking `remaining_budget_mismatch` error rather than a warning.
- [ ] `backend/pricing.py:105-106` — `discount()` is hard-coded to always return `0.0`; a real branch of `PricingBreakdown` that can never produce a nonzero value, leaving `discount` fields in `Recommendation`/`RepriceResponse` permanently dead until implemented.
- [ ] `backend/app.py:90` — `summary_lines[:3]` truncates silently with no "+N more" indicator; once `invalid_category` is fixed to actually render, 4+ distinct warning groups would drop one with no signal anything was omitted.
- [ ] `backend/catalog_loader.py:16-29` — `"Tag"` is listed as an alias for both `"category"` and `"tags"`; a sheet with only a `Tag` column derives both fields from the same column, fragile if their semantics diverge.
- [ ] `backend/data_provider.py:222-226` — cache-file extension is derived from whichever `filename` was last uploaded; a CSV upload followed by an xlsx upload (or vice versa) can each write a differently-suffixed cache file without cleaning up the stale one.
- [ ] `frontend/src/components/BriefWizard.jsx:41` — hardcoded `"up to 10"` hint string instead of referencing `MAX_ITEM_COUNT` (already imported); the "Number of options" field two lines below does this correctly via template literal, so this one's just missed.
- [ ] `frontend/src/components/ResultsPanel.jsx:39-49` / `RecommendationCard.jsx:20` — array index used as React `key` on a list that reorders between generates; currently harmless (no local component state), but fragile against future changes.
- [ ] `frontend/src/App.jsx:27-30,144-147,163-166` — the catalog-range/product-names computation (`Math.min/max` over `selling_price`, mapping names) is duplicated verbatim across three async functions (initial load, pull-now, upload).
- [ ] `frontend/src/config/brief.js:12-15` — category-name strings are duplicated between `categories` and each preset's `categories` array; adding/renaming a category requires updating multiple literals by hand.
- [ ] `frontend/src/lib/briefForm.js:36-43` — `bestFuzzyMatch` recomputes Levenshtein similarity against every catalog product name on every `classifyMustInclude` call, with no memoization; a real (if currently small) perf cost that grows with the catalog.

## Should be removed

- [ ] `backend/recommender.py:17,32` — `_search_pool` and `_search_unique_pool` are imported directly but never called in this file; all search goes through `generate_combinations`.
- [ ] `backend/recommender_search.py` (`allow_repeats` parameter and its branches, ~1/3 of `_search_pool`'s body) — `allow_repeats=True` is never passed anywhere in the codebase; the unbounded/"item may repeat" transition and reconstruction logic is unreachable.
- [ ] `backend/app.py:189-208` + `backend/intent_parser.py` entirely — no frontend code calls `/api/intent/parse` or `/api/intent/recommendations` (grepped `frontend/src`, zero matches); the whole intent-parsing path looks dead from the product's perspective. **Verify intent before removing** — may be deliberately held for a future feature rather than abandoned.
- [ ] `backend/excel_loader.py` — a pure re-export shim over `catalog_loader.py` with no behavior of its own; only its own test file imports it.
